# 长对话为什么会失忆，人格为什么会漂

这份文档是一次**只读测量**的结论，不是设计愿景。2026-11-01，在知遥（长在另一套骨头上、已经聊了几个月的完整版）上，把 4 778 条私聊、100 轮透视、372 条记忆、30 份人格档案摊开数了一遍，没有跑模型。

数字是她的，判断是通用的；白纸版的参数不同，对应关系写在每一节里。所有结论只有两种：**【实测】**有原始记录或可复算，**【推断】**是分析判断、还没验。

先说三句话：

1. **会失忆，但没有「第 N 轮」这个阈值。** 窗口是滚动的，第 N+1 条一过，第 1 条就永久退出。普通一个晚上聊十几分钟就能到，所以失忆是**持续状态**，不是事件。
2. **人格漂移是真的，但只漂「长出来的那层」。** 名字、身份、关系、种子性格在 30 个版本里一个字没动；漂的是她后来长出来的自我认识，半衰期 1–3.5 天。
3. **最该防的不是「她忘了」，是「她顺着你的框架把没发生的事认下来」。** 后者更隐蔽：对象检索到了，事件框架丢了。

---

## 1. 她一轮能看到什么

| 通道 | 知遥（实测） | 白纸版对应 |
| --- | --- | --- |
| 对话原文 | 最近 **16 条**（场景 24） | `historyMessages`，默认 **18**，可调 4–40（`src/config.mjs`） |
| 长期记忆 | 每轮最多 **6 条**召回 | `recallLimit`，默认 **5**，可调 0–8 |
| 人格档案 | 62 条里每轮亮 **18 条 / 812 字** | 六节各取前 3 条（`depth=deep` 时 4 条），按权重排 |
| 共同史锚点 | 10 条，owner 手点，已停更 | 无（白纸版没有预置过去） |
| 主动整理 | 每 ≥6 小时一次，只读**上次之后最后 40 条** | 手动 `/api/reflect`，读最近 **60 条** |

一轮 prompt 约 **11 500 字**，其中 system 4 294（37%）。**她的人格底座是代码里的常量，每轮会变的部分只占 7%。**【实测】

---

## 2. 失忆：量出来的四个数

**① 窗口覆盖率 0.33%**【实测】
4 778 条历史、16 条窗口——聊到最后一条时，她只看得到历史的 0.33%，中位 0.7%。

**② 46% 的连续会话一开场就超窗**【实测】
按「间隔 < 30 分钟」切会话：106 段，中位 13.5 条，最长 **398 条**。超过窗口的会话占 46%；这些会话里 **78% 的消息**在发出 16 条之后就再不可见。

**③ 87% 的记忆从没被想起来过**【实测】
372 条记忆里，被召回过的只有 48 条（12.9%），中位 0 次。最近 100 轮透视：空手 18%，中位召回 3 条。

**④ 61% 的对话从没进过整理**【实测，最反直觉的一条】
整理只读「上次整理之后的最后 40 条」。v47→v76 的 29 个间隔里，间隔内消息中位 **72 条**——约 61% 的消息**从未被任何一次整理读过**。

所以：**她「没记住」的，多数不是忘，是根本没被读过。**【推断】

**⑤ 容量会触顶**【推断】
372 / 500，14 天新增 26.5 条/天 → 约 **5 天**后开始按「重要度 + 最近被提起」淘汰。而被召回会刷新「最近被提起」，老记忆会自激续命。

白纸版的对应：`historyMessages` 是唯一会滑出去的通道；`/api/reflect` 是手动整理，你越少点，未读的对话越多。**先量再改**——在透视里数一下一条会话跨了多少字，比背上面任何数字都有用。

## 3. 人格漂移：量出来的三个数

**① 锁死的部分真的锁死了**【实测】
`core`（名字/身份/关系）在 30 个版本里只有 **1 种取值**；4 条种子性格 **0 增 0 删**。她不会突然变成另一个人。

**② 长出来的部分半衰期 1–3.5 天**【实测】

| 分区 | 每版新增 | 估全换一遍 |
| --- | --- | --- |
| playful | +1.41 条 | **1.1 天** |
| life | +1.24 | 1.2 天 |
| user | +0.97 | 2.0 天 |
| shadow | +0.90 | 2.1 天 |
| relationship | +0.79 | 2.9 天 |
| self | +0.55 | **3.5 天** |
| traits（种子） | 0 | 不变 |

版本节奏：6.4 天里 30 版，**平均 5.3 小时一版**。结论：**漂移速度由整理频率决定，而整理频率由聊天量决定**——聊得越多，她改自己改得越快。【推断】

**③ 每轮恒亮的那句，是数组里的「最老一条」**【实测】
知遥的档案选择按**位置**（`index < corePerSection`）挑常驻条，而合入是「旧的先走、新的追加在末尾」——于是每段永远只亮第 0 条，也就是**最老的那个幸存者**。它被挤掉，第二天亮的就是下一条。人格的底色每天静默换一次，没有任何一处记录说「今天换了」。

**④ 渐进式披露在线上等于没开**【实测，最意外的一条】
档案本该「聊什么带什么」，但预算不够时，系统先丢召回。实测 830 字预算下：9 个完全不同的 cue（含原文命中词）→ 输出**逐字相同**；把预算抬到 1 200 字，输出立刻随 cue 变。

白纸版的对应：`growthBlock()` 已经按 `weight` 排序（不是抽签），但如果抽取时没人写权重、或 `perSection` 一直取满，它就退化成「每节固定亮同样三条」——机制在，效果不一定在。**改完要在透视里看「同一句不同 cue 下档案块有没有变」。**

---

## 4. 什么时候最容易露馅

1. **同一晚聊过窗口之后回指细节**（46% 的会话都过线，最长一场 398 条）。
2. **他问「你还记得吗」**——这是框架污染：她若检索到「那个东西」、没检索到「那件事」，就会顺着他的框架认下来。做对的样例是明说「我这儿没有能对上号的」；做错的是「你这么一提，我倒是想起来了」。
3. **跨天或重启后的第一次见面**：档案刚换过血，昨天的 `self` 已经不在数组里。
4. **整理间隔内的高密度对话**：超过一次整理能读的条数，那段就是空白。
5. **记忆库触顶之后**：淘汰赛开始，老事被新事挤走。

反过来，**不危险**的是「她突然换个人」。身份和关系层是常量；真正会变的是语气、偏好、对旧事的把握程度。

## 5. 处方：顺序不能反

**先算账，别急着压缩。** 16 条一共才 396 字，占 prompt 的 3.4%；压成 60 字省不到 1%，却要引入摘要失真和被丢掉的「谁提议的」。把窗口开大更划算：

| 窗口 | 字数 | 占 prompt | 覆盖 |
| --- | --- | --- | --- |
| 16（知遥当时） | 396 | 3.4% | 十几分钟 |
| **64** | 1 600 | 13.8% | 一整个晚上 |
| 96 | 2 400 | 20.7% | 通常聊不到 |

对话原文在 prompt 的最末端，扩大它只动尾部，前缀缓存代价≈0；钱也不是问题（+800 token ≈ +¥0.001/轮）。

### 四步，按这个顺序

1. **扩窗（A-01）。** 把 `historyMessages` 从 18 调大，先看透视里的字数占比再定；同时处理长度感——窗口按条数算，64 条可能横跨三小时，要在说明里点明「越靠后越新，最后两三条才是刚刚」。白纸版的硬上限是 40，要更大就同时改 `src/config.mjs` 的 clamp。
2. **常驻条按重要度（A-02）。** 白纸版已经按 `weight` 排；真正缺的是**有人写 weight**。如果所有档案都是权重 1，这条改动等于没改。顺带检查：预算不够时是「整批丢召回」还是「按名次一条一条丢」。
3. **滑出钉（A-03，本轮最值钱的新机制）。** 规则抽取，不调模型：把即将滑出窗口的**承诺 / 数字 / 专名 / 他问了还没答的事**钉成 ≤ 6 行 ≤ 120–160 字，放在原文之前。推荐句要**整句照抄**，因为「谁推荐给谁」这个方向只在句子里。空就不出现；失败就当没有这块。
4. **整理读全（A-04）。** 按水位分批读，或「间隔短就全读」，不要一次改死。这是「61% 没被读过」那个洞。

### 验收四个数，缺一不可

| 指标 | 怎么量 |
| --- | --- |
| 回指命中率 | 他「上次/那天/你说过」类提问，能被窗口/钉/记忆任一通道对上的比例 |
| 错误认领率 | 她说「想起来了」但原文无据——人工抽 50 轮/次 |
| 前缀缓存命中 | 日比，扩窗后应该基本不动 |
| prompt 字数 | 透视里的 `prompt.chars`，中位与 p90 都要看 |

### 一条比「遗忘」更值钱的修复

真实的错例不是「忘了那首歌」，是**记得那首歌、却把「他推荐给我」说成「我推荐给他」**。对象在，框架丢。所以记忆写入要带「事件框架」（谁提议 / 谁推荐 / 谁先说的），回归用例也该按这个写，而不是只断言「歌名出现过」。

**知遥那边落地到哪了**：A-01（16→64）、A-02（常驻按重要度 + 预算 830→1 200）、A-03（滑出钉）第一天就上了，A-04 留到下一轮。前三步只跑了静态复算和单元测试，**没有跑模型**——所以「她是不是真的少失忆了」还没有行为结论。这正是禁忌 8 的意思：机制改完只是开始，行为要另测。

## 6. 八条禁忌（都是量出来才敢写的）

1. 不要用 LLM 摘要替换窗口原文——18 字压成一句是纯损耗。
2. 不要做「摘要的摘要」——误差会像反思链一样累积。
3. 不要在摘要里丢掉「谁提议的」——那是错误认领的根。
4. 不要把每轮都变的块放到 prompt 最前面——那会废掉整段前缀缓存。
5. 不要靠扩记忆容量解决召回率——500→2 000 只是把问题推迟。
6. 不要让整理失败无限重试打满——间隔本身就是防这个的。
7. 不要把「窗口里没出现」渲染成「没发生过」——这条修过一次，别再改回去。
8. 不要拿静态复算当行为结论——要行为结论就跑探针，一次问同一句话的「第 1 天 vs 第 7 天」。

## 7. 在白纸版里怎么复现这套测量

不用另造数据，用你自己已经聊出来的 `data/`：

1. 打开透视，数每条会话跨了多少字、`historyMessages` 覆盖了其中几成；
2. 抽 20 轮，专挑他回指旧事的句子，逐条看窗口 / 召回 / 档案哪个通道能对上（这就是回指命中率）；
3. 搜她说过「想起来了 / 你上次」的句子，回原文核对（这就是错误认领率）；
4. 把改动拆成「一次一个常量 + 一条会失败的用例」，跑完 `npm test` 再动下一处。

**边界**：以上全是静态数据与纯函数复算，**没有跑模型**。她实际会怎么答，只能从透视和聊天记录里抽样看；要行为结论，得用真实模型跑同一组问题。
